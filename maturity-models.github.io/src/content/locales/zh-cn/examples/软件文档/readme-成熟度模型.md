# README 成熟度模型

## 一级：“代码即文档”

- 没有任何形式的 README 文本，或几乎没有。
- 没有安装、配置、运行的详细说明。
- 没有开发者文档。
- 没有配套文件，例如贡献者指南。
- 没有构建状态信息，因此无法了解项目的当前状态。
- 没有建议的议题和/或拉取请求平均响应时间。
- 没有显示代码覆盖率或其他质量指标的徽章。
- 现有文本可能已过时或不是优先事项。

**建议**：开发者有时会发布尚未准备好分享的个人项目和实验。在这些情况下，几乎没有文档或完全没有文档可能是可以接受的。我们建议 README 说明项目的性质/状态。例如，提醒用户“此项目为实验性/个人项目，请自行承担使用风险。”

## 二级：最低限度的 README

- 关于项目功能和目的的信息有限。
- 面向用户的基本安装、配置、运行细节，但未经测试且不完整。
- 基本的开发者文档，或没有。
- README 中有一行关于贡献的内容，但没有专门的文件。
- 有一行关于项目构建状态的内容，尽管可能已过时；或者没有构建状态信息。
- 有一行关于议题和/或拉取请求平均响应时间的内容。
- 没有显示代码覆盖率或其他质量指标的徽章。
- 文本很少更新，可能已过时或不准确。

**建议**：二级 README 面向广泛的受众，但其不完整会造成挫败感和徒劳的努力。有时这比完全没有文档更糟。请加入一条说明，指出项目是处于早期阶段、不稳定、实验性还是个人项目。

## 三级：基本 README

- 有一些关于项目功能、用途和目的的详细信息。
- 面向用户的基本安装、配置、运行细节，已测试且完整。
- 面向潜在贡献者的基本文档。
- 用于引导新贡献者的愿景声明或项目路线图。
- 带有基本信息的 Contributing.md/.rst 文件。
- 有一行关于项目构建状态的内容，但很简略：“开发中”或“稳定”。
- 有一行关于议题和/或拉取请求平均响应时间的内容。
- 至少有一个显示代码覆盖率或其他质量指标的徽章。
- 文本按月度或季度间隔更新，因此可能存在不准确之处。

**建议**：三级 README 足够全面，可以支持小规模社区增长。需要发展贡献者的早期项目应在发布前力争达到这一级别。项目可能获得广泛采用，尽管 README 可能构成障碍。

## 四级：有目的的 README

- 关于项目目的、功能和特殊特性/属性的详细信息。
- 详细的用户安装、配置和运行说明，可能最近更新过，也可能没有；包含常见错误及其解决方法的信息。
- 面向潜在贡献者的详细文档。
- 用于引导新贡献者的详细愿景声明或项目路线图。
- 带有详细风格指南的 Contributing.md/.rst 文件。
- 构建状态指出项目中不完整和/或造成不稳定的具体方面。
- 关于议题和/或拉取请求平均响应时间的清晰信息。
- 一个或多个显示代码覆盖率或其他质量指标的徽章。
- 文本按月度或季度间隔更新，因此可能存在不准确之处。

**建议**：四级 README 可以支持大规模的社区使用和增长。它可能缺少实现广泛使用和采用所必需的某些要素。对采用设有严格标准的企业在使用它之前可能会犹豫。

## 五级：面向产品的 README

- 关于项目目的、功能和特殊特性/属性的详细信息，使读者能够立即理解其特性和属性的用处与影响。
- 用户评价以及在真实开发情境中过往表现的证据。
- 详细的用户安装、配置和运行说明，经过测试且是最新的；包含常见错误及其解决方法的信息。
- 面向潜在贡献者的详细文档。
- 用于引导新贡献者的详细愿景声明或项目路线图。
- 嵌入的视觉辅助，如图表和演示。
- 带有详细风格指南的 Contributing.md/.rst 文件。
- 构建状态指出项目中不完整和/或造成不稳定的具体方面。
- 关于议题和/或拉取请求平均响应时间的清晰信息。
- 一个或多个显示代码覆盖率或其他质量指标的徽章。
- 文本按周甚至按日间隔更新，因此不太可能出现不准确之处。

**建议**：五级 README 通常出自拥有广泛贡献者/用户群的项目。其详尽程度强化了可用于生产的使用和受监督的贡献。每个项目都应力争达到这一级别的文档。
