# 基础设施即代码（IaC）成熟度模型

出处：https://programmaticponderings.com/2016/11/25/infrastructure-as-code-maturity-model/


## IaC -1 级：倒退

流程不可重复、控制不佳、被动应对

  * 只有有限的基础设施以代码方式供给和管理
  * 基础设施供给仍然需要许多手动流程
  * 基础设施代码没有使用行业标准的工具和模式编写
  * 基础设施代码没有作为流水线的一部分进行构建、单元测试、供给和管理
  * 基础设施代码、流程和程序的文档记录不一致，并非所有需要的相关方都能获取

## IaC 0 级：可重复

流程已有文档记录并部分自动化

  * 所有基础设施代码和配置都存储在集中的版本控制系统中
  * 基础设施的测试、供给和管理作为自动化流水线的一部分完成
  * 基础设施可以按单个组件部署
  * 利用对物理设备的编程接口
  * 对组件和依赖项进行自动化安全检查
  * 自助服务的 CLI 或 API，内部客户自行供给其资源
  * 所有代码、流程和程序都有文档记录且可获取
  * 不可变基础设施和流程

## IaC 1 级：一致

自动化流程应用于整个应用程序生命周期

  * 基础设施的供给和管理完全自动化
  * 尽量少使用不受支持的“自制”基础设施工具
  * 单元测试满足代码覆盖率要求
  * 每次向版本控制系统签入时都会持续测试代码
  * 使用零停机供给实现持续可用的基础设施
  * 使用配置注册表
  * 配置文件模板化（没有 awk/sed 的黑魔法）
  * 机密信息得到安全管理
  * 基于用户定义的负载特征进行自动伸缩

## IaC 2 级：量化管理

流程已被度量和控制

  * 使用基础设施定义文件
  * 能够自动回滚
  * 基础设施和支持系统高度可用且容错
  * 外部化配置，没有用于修改配置的黑盒 API
  * 基础设施受到全面监控，并带有可配置的告警
  * 聚合的、可审计的基础设施日志
  * 所有代码、流程和程序都在知识管理系统中有良好的文档记录
  * 基础设施代码使用声明式而非命令式的编程模型，也许……

## IaC 3 级：优化

聚焦流程改进

  * 自愈、自配置、自优化的基础设施
  * 对照业务 KPI 进行性能测试和监控
  * 最大化的基础设施利用率和工作负载密度
  * 遵循云原生和 12 要素（12-Factor）模式
  * 与云无关的代码，最大限度减少对云供应商的锁定
