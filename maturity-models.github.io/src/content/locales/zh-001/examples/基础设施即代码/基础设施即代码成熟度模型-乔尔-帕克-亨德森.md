# Joel Parker Henderson 的基础设施即代码（IaC）成熟度模型

基础设施即代码（IaC）是通过机器可处理的文件（源代码、脚本、声明式文件、点文件等），而不是物理硬件配置或交互式工具，来管理和供给计算基础设施（流程、裸机服务器、虚拟服务器等）及其配置的过程。

参见维基百科：
* [Infrastructure as Code](https://en.wikipedia.org/wiki/Infrastructure_as_Code)
* [Continuous configuration automation (CCA)](https://en.wikipedia.org/wiki/Continuous_configuration_automation)
* [DevOps](https://en.wikipedia.org/wiki/DevOps)
* [Maturity model](https://en.wikipedia.org/wiki/Maturity_model)


## 0 级：无

*  没有 IaC，或使用可忽略，或不适用。


## 1 级：起步 + 非正式

* 基础设施即代码处于起步阶段，包括评估、试验项目、试点、原型等领域。

* 项目中的队友开始谈论 IaC，通常是由一位英雄或一小群想要它的人推动。

* IaC 代码的质量往往是手工编写、手工测试或手工配置工具。

* 应用规划聚焦于交付代码。

<b>示例：</b>

* 使用云服务，例如 Amazon Web Services。

* 使用 shell 脚本检查服务器的运行时间

<b>改进思路：</b>

* 从使用手工的一次性安装，转向使用 apm、apt、brew、choco、melpa、gem、pip、yum 等包管理器，以及配置文件和点文件等配置管理。

* 了解任何流行的主流配置工具，例如 Ansible、Salt、Puppet、Chef。


## 2 级：发展 + 描述

* 基础设施正在发展，通常是出于团队的需要。此级别的典型软件通常包括云服务（如 AWS）、容器化（如 Docker）、配置管理（如 Ansible）、编排工具（如 Kubernetes）、持续交付软件（如 GoCD），以及可能的平台即服务产品（如 Heroku）。

* 部门的队友在谈论 IaC，并致力于寻找利用 IaC 在多个项目中帮助部门的方法。

* 代码质量开始除了应用代码之外，也为 IaC 代码使用自动化测试。

* IaC 的支持者发展并描述跨职能领域，例如成本（降低）、速度（执行）和风险（缓解）。

* 应用规划包括文档，理想情况下着眼于开发各种操作手册（cookbook）、配方、清单、蓝图，以及开发运维（devops），例如持续集成、作为应用交付过程组成部分的部署流水线，以及涵盖整个交付流水线的质量保证。


<b>示例：</b>

* 至少有几个项目，开发人员可以提交一行代码，代码通过持续集成、持续交付，以及可选的功能开关、限流发布（蓝/绿、go/no-go、金丝雀发布等）能力流入生产环境。

* 部门使用源代码仓库共享 IaC 代码并开展 IaC 协作，还可选择使用聊天、帮助、文档、wiki、规划等能力。

<b>改进思路：</b>

* 技术方面：以与团队项目代码一致的方式开发 IaC 代码，例如进行代码评审、路线图规划、幂等性测试等。熟悉上述所有示例：AWS、Docker、Ansible、Kubernetes、GoCD、Heroku；即使您选择使用它们的替代品，所学知识也能很好地迁移。

* 社交方面：与其他团队分享 IaC 代码，获取反馈，并改进代码及其在协作、文档、验证等方面的所有相关能力。


## 3 级：标准化 + 规模化

* 基础设施正在标准化，通常得益于团队创建规范、可共享的代码和源代码仓库。

* 团队成员可以快速、自信、有效地创建 IaC 项目，包括端到端的成功以及任何文档和认证。

* 代码质量朝着面向服务的能力迈进，例如 API、可发现性、可混合性。

* IaC 的方法通常是命令式和/或过程式的。命令式方法关注如何更改基础设施以满足目标配置。命令式方法定义需要执行的具体命令，以得出期望的结果。

* IaC 的支持者将跨职能领域标准化，例如成本（降低）、速度（执行）和风险（缓解）。标准化包括具体的权衡，例如更快部署的成本/收益，或安全验证的风险/回报。

* 应用规划包括为自标准化和/或自伸缩而设计，以及不可变基础设施、凤凰服务器、IaaS、PaaS 和 iPaaS 等 devops 技术。

<b>示例：</b>

* 通常项目可以一键部署，包括按需即时创建相关资源、数据库、网络、地址等。

* IaC 的使用不仅限于 IT 部门；这可能包括自助服务工具（例如设置新笔记本电脑），也包括重要的业务工具（例如 IT-业务团队可以独立于 IT 系统管理员配置和部署新服务）。

<b>如何改进：</b>

* 技术方面：学习如何将 IaC 代码模块化并分发，例如使用包管理器、模块、库、功能分解、幂等性测试、热重载等。

* 社交方面：明确规划良好的治理。治理包括技术领域（如版本管理和发布管理）、团队领域（如五问法根因分析和不问责的回顾）以及管理领域（如预算和审批）。


## 4 级：管理 + 度量 + 使命

* 基础设施与明确的使命陈述协同管理和度量。较好的候选方案有 [OKR（目标与关键成果）](https://github.com/joelparkerhenderson/objectives_and_key_results)、[KPI（关键绩效指标）度量](https://github.com/joelparkerhenderson/key_performance_indicator)和[战略平衡计分卡](https://github.com/joelparkerhenderson/strategic_balanced_scorecard)。

* 团队成员可以轻松使用记分牌、仪表板、指标、度量以及类似的数据驱动工具来运行、升级和验证 IaC 代码。IT 高管可以轻松使用汇总系统来证明 IT-业务能力和成本合理性。

* 使用持续交付工具、自动化代码质量审查、规模化基准测试等，持续度量和测试代码质量。

* IaC 的方法通常是声明式和/或函数式的。声明式方法关注最终的目标配置应该是什么。声明式方法定义期望的状态，由系统执行实现该期望状态所需的操作。

* IaC 的支持者在跨职能领域证明成功，例如成本（降低）、速度（执行）和风险（缓解）。证明包括更快部署的成本/收益数据、安全验证的风险/回报等。

* 应用规划包括为自管理和/或自度量而设计。

<b>示例：</b>

* 许多项目从日出到日落，端到端一键启动。这可以包括应用生命周期管理（ALM）、组合、项目群与项目管理（PPPM）、最佳实践、成熟度模型匹配等。

* IaC 工具会输出指标，这些指标又可用于应用性能监控（APM）、合成监控、调试和能力增长规划。

<b>如何改进：</b>

* 技术方面：改进代码，使其适合主流使用。这包括对边界情况、故障模式、混沌干扰、中断缓解措施的全面测试覆盖。

* 社交方面：从长期管理和主流使用的角度规划 IaC，包括生命周期管理、资金管理、沟通管理、价值流映射和治理管理的路线图。


## 5 级：优化 + 编排 + 机遇

* 为基础设施的研究与开发提供资金，以创造新的产品和服务，以及新的商业机会。

* 代码质量能够持续演进，并欢迎整个组织，以及可能的合作伙伴、供应商、客户和公众的贡献、讨论和使用。

* IaC 的方法是编排式的，并具有环境感知能力。编排式方法关注为什么配置应该是某种样子，考虑到生产环境中通常存在的、运行在同一基础设施上的多个应用之间的所有相互关系和相互依赖。

* IaC 的支持者在跨职能领域优化成功，例如成本（降低）、速度（执行）和风险（缓解）。优化包括更快部署的成本/收益数据、安全验证的风险/回报等。优化还包括战略性的前瞻，以推动组织在这些跨职能领域的投资。

* 应用规划包括为自优化和/或自愈而设计。

<b>示例：</b>

* Amazon 创建 AWS，Google 创建 GCS，Facebook 创建 React，Netflix 创建许多开源项目。

* 使用 Kubernetes 和 Mesos 等工具在内部和外部的多个云之间进行编排。

<b>如何改进：</b>

* 创建能激励人们培养更多 IaC 能力的代码。这包括公开代码，例如撰写博客介绍它、为它创建帮助渠道，并教授如何使用它。

* 利用 IT 推动战略机遇，例如对公司、产品和人才的投资。
