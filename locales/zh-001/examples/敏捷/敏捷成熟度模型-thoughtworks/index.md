<h2><a name="构建管理与持续集成">构建管理与持续集成</a></h2>

-1 级：
* 构建软件的流程为手动。
* 不管理制品和报告。

0 级：
* 定期的自动化构建和测试。
* 任何构建都可以通过自动化流程从源代码控制中重新创建。

1 级：
* 每次提交变更时都执行自动化的构建和测试循环。
* 管理依赖项。
* 复用脚本和工具。

2 级：
* 收集构建指标，使其可见，并据此采取行动。
* 不留下损坏的构建。

3 级：
* 团队定期开会讨论集成问题。
* 团队通过自动化、快速反馈和更高的可见性来解决问题。


<h2><a name="环境与部署">环境与部署</a></h2>

-1 级：
* 部署软件的流程为手动。
* 特定于环境的二进制文件。
* 环境手动供给。

0 级：
* 向部分环境自动化部署。
* 创建新环境成本低廉。
* 所有配置均外部化/带版本。

1 级：
* 完全自动化的自助式一键流程来部署软件。
* 所有环境使用相同的部署流程。

2 级：
* 管理编排式部署。
* 发布和回滚流程经过测试。

3 级：
* 所有环境都得到有效管理。
* 供给完全自动化。
* 在适当时使用虚拟化。


<h2><a name="发布管理与合规">发布管理与合规</a></h2>

-1 级：
* 发布不频繁且不可靠。

0 级：
* 痛苦且不频繁，但可靠的发布。
* 从需求到发布的可追溯性有限。

1 级：
* 定义并执行变更管理和审批流程。
* 满足监管和合规条件。

2 级：
* 监控并主动管理环境和应用程序的健康状况。
* 监控周期时间。

3 级：
* 运维团队和交付团队定期协作，以管理风险并缩短周期时间。


<h2><a name="测试">测试</a></h2>

-1 级：
* 开发之后才进行手动测试。

0 级：
* 自动化测试作为故事开发的一部分编写。

1 级：
* 自动化单元测试和验收测试，后者与测试人员共同编写。
* 测试是开发过程的一部分。

2 级：
* 跟踪质量指标和趋势。
* 定义并度量非功能性需求。

3 级：
* 生产环境回滚很少见。
* 缺陷被立即发现并修复。


<h2><a name="数据管理">数据管理</a></h2>

-1 级：
* 数据迁移没有版本，且手动执行。

0 级：
* 对数据库的变更使用与应用程序一起带版本的自动化脚本完成。

1 级：
* 数据库变更作为部署流程的一部分自动执行。

2 级：
* 每次部署都测试数据库升级和回滚。
* 监控并优化数据库性能。

3 级：
* 数据库性能和部署过程在各个发布之间形成反馈环。
