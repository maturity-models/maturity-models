# Prowareness 敏捷团队成熟度模型

参见 [Prowareness Team Maturity Model](http://agilityladder.nl/files/2015/06/Prowareness-Team-Maturity-Model_presentation.pdf)

<table>

<tr>
<th></th>
<th>1 级<br>新手</th>
<th>2 级<br>进阶初学者</th>
<th>3 级<br>胜任</th>
<th>4 级<br>熟练</th>
<th>5 级<br>专家</th>
</tr>

<tr>

<th>文化</th>

<td>
纪律：
<ul>
<li>团队文化体现出对应用组织所规定实践的有纪律的态度。
</ul>
<p>
行为：
<ul>
<li>遵守规则，聚焦实践的目标
<li>理解并解释这些实践为什么重要
<li>从钢铁侠到复仇者联盟
</ul>
</td>

<td>
信任：
<ul>
<li>团队文化的特点是追求持续改进和学习。
</ul>
<p>
行为：
<ul>
<li>实验
<li>回顾会议聚焦改进
<li>快速失败、频繁失败、尽早失败的心态
<li>从羞耻与自焚到声誉与学习
</ul>
</td>

<td>
支持：
<ul>
<li>团队的选择和努力得到组织的支持。
</ul>
<p>
行为：
<ul>
<li>寻求帮助
<li>辅导、指导和导师制是推动团队沟通的关键要素
</ul>
</td>

<td>
延伸：
<ul>
<li>借助（组织的）愿景，团队文化可以拓展边界，使产品和团队的成果最大化。
</ul>
</td>

<td>
专家：
<ul>
<li>信任胜于合同
<li>支持胜于控制
<li>纪律胜于合规
<li>延伸胜于约束
</ul>
<p>
文化：
<ul>
<li>每个人都深切关心所有利益相关方
<li>每个人都承担明智的风险
<li>每个人都把变化视为机遇
<li>每个人都聚焦成果
</ul>
</td>

</tr>

<tr>

<th>IT</th>

<td>
基础 Scrum
<p>
良好实践：
<ul>
<li>冲刺规划
<li>发布规划
<li>每日 Scrum
<li>了解完成定义（DoD）、就绪定义（DoR）、故事点定义
<li>待办列表梳理
<li>冲刺内演示与预演示
<li>冲刺评审
<li>回顾会议
<li>Kaizen（改善）
</ul>
</td>

<td>
代码质量
<p>
良好实践：
<ul>
<li>度量代码指标
<li>静态/动态代码分析标准
<li>持续集成
<li>测试驱动开发（TDD）
<li>结对编程
</ul>
</td>

<td>
自动化质量保证
<p>
良好实践：
<ul>
<li>自动化单元测试
<li>自动化集成测试
<li>自动化回归测试
<li>代码覆盖率管理
<li>测试环境搭建
<li>工具选型
</ul>
</td>

<td>
规模化
<p>
良好实践：
<ul>
<li>架构文档
<li>度量架构债务
<li>DTAP——开发、测试、验收和生产
<li>统一的技术栈
<li>拥有规模化模型
<li>Scrum 之 Scrum
</ul>
</td>

<td>
持续交付
<p>
良好实践：
<ul>
<li>自动化部署
<li>环境定义（基础设施即代码）
<li>基础设施供给与维护
<li>回滚机制
<li>向前滚动机制
<li>主干开发
<li>功能开关
<li>编排管理器解决方案
<li>流水线检查与指标
</ul>
</td>

</tr>

<tr>

<th>业务</th>

<td>
待办列表管理
<p>
良好实践：
<ul>
<li>实施产品待办列表项类型
<li>针对不同用户实施不同场景
<li>可视化产品待办列表内容
<li>可视化产品待办列表进度
</ul>
</td>

<td>
让最终用户/客户参与
<p>
良好实践：
<ul>
<li>利益相关方与开发团队的对话
<li>在冲刺评审中让利益相关方感到惊喜
<li>可靠的预测（更窄的不确定性锥）
<li>发布工作坊
<li>客户拜访
<li>利益相关方分析
</ul>
</td>

<td>
直接的客户反馈
<p>
良好实践：
<ul>
<li>自愿参加冲刺评审
<li>客户参加梳理会议（受邀）
<li>评审时的客户满意度
<li>可发布的增量
<li>共同的愿景
</ul>
</td>

<td>
端到端价值
<p>
良好实践：
<ul>
<li>端到端产品负责人
<li>联合梳理
<li>集成式产品评审
<li>团队成员扮演最终用户
<li>端到端规划
<li>规模化敏捷框架
</ul>
</td>

<td>
价值导向
<p>
良好实践：
<ul>
<li>识别价值、目标和 KPI 假设
<li>识别假设
<li>对产品待办列表项进行价值估算
<li>最小可行产品
<li>度量价值
<li>短周期的构建、发布、度量与改进循环
<li>A/B 拆分测试
<li>可视化已验证的价值
</ul>
</td>

</tr>

<tr>
<th>团队</th>

<td>
团队由招聘人员、开发经理和 Scrum 主管组建
<ul>
<li>战略由组织决定
<li>技术栈的使用由组织决定
<li>会议结构由组织规定
<li>没有质量关口，凭个人判断
</ul>
</td>

<td>
部门
<ul>
<li>团队参与团队成员的招聘和绩效评审
<li>产品战略由组织决定
<li>各团队就提高代码质量所需的技术保持一致
<li>会议结构由组织决定
<li>关闭质量反馈环（如缺陷分析、不问责的事后复盘）
</ul>
</td>

<td>
特许经营
<ul>
<li>团队根据组织设定的指导方针，负责团队构成、招聘和绩效评审
<li>产品战略与组织共同创建
<li>团队负责测试自动化以及最能帮助他们的工具
<li>除跨团队/部门会议外，团队可自由决定自己的会议结构
<li>带有主动监控的自动化质量关口
</ul>
</td>

<td>
自给自足的单元
<ul>
<li>团队作为自给自足的业务单元运作，承担端到端的责任
<li>团队根据组织的愿景创建自己的产品战略
<li>团队对最适合交付端到端价值的技术栈有清晰的看法
<li>团队可在整个价值链中自由决定自己的会议结构
<li>自动化质量关口、主动监控、A/B 测试和决策
</ul>
</td>

<td>
精益创业
<ul>
<li>团队像公司一样运作
<li>团队据此创建自己的产品愿景和产品战略
<li>团队对最适合交付端到端价值的技术栈有清晰的看法
<li>团队可自由决定会议结构
<li>自动化质量关口、主动监控、A/B 测试、频繁发布、直接的客户反馈和决策
</ul>
</td>

</tr>

</table>
